Overview
########
########

Stream protocol is used to establish data streams between clients.
They can be used for various purposes: voice and video calls, screen sharing,
etc.

Stream management is described in the ClientProtocol and GateProtocol
documents.

Point to point stream structure
###############################
###############################

The stream is a sequence of datagrams.
Each datagram has the following structure:
| MAC | nonce | encrypted payload |

Payload size must not exceed 1 KB in order to fit UDP packet size.

When the connection between clients is established, the clients may have
any number of logical streams between them. Each logical stream is used
by one subsystem (e.g. first stream for voice data, second stream for video
data).

Each direction has its own namespace of stream identifiers. For example,
stream number 1 from client A to client B has no relation to stream number 1
from client B to client A.

So, the datagram payload has the following structure in decrypted state:
| DATA | logical stream id | data size | data |

Control datagrams have another structure:
| CONTROL | action |

Action types:
| REQUEST_STREAM | stream type | stream id | -- request new outbount stream.
| ACCEPT_STREAM | stream id | -- accept new inbound stream.
| DECLINE_STREAM | stream id | -- decline new inbound stream.
| END_STREAM | stream id | -- end outbound stream.

| SWITCH_TO_UDP | sender IP address | sender port | -- request switching to UDP.
| ACK_UDP | -- confirm getting packages via UDP.
| UDP_FAILURE | -- notify about critical data loss via UDP.

Stream types:
AUDIO
VIDEO
CUSTOM

Direct client connection
########################

The clients may establish direct connection via UDP to reduce server load.
In this situation congestion control and stream consistency check must
be done by the clients since TCP is not used.

Direct connection is used only for datagrams with data. Control datagrams must
be sent via the server.

Datagrams sent via UDP have the following structure:
| MAC | nonce | datagram id | confirmed datagram id | payload |
              \         encrypted part of the datagram        /

The datagram id is the number of datagram in the sequence.

Confirmed datagram id is the number of datagram previously received by the
datagram sender. It is used to acknowledge the other client that the
datagram was received. It there is no datagram to acknowledge, this field
must have a value -1.

A datagram without payload can be sent if there is no data to be sent and a
received datagram needs to be acknowledged.

Example:
Client A            Client B
| -----------------------> |
|   | 1 | -1 | payload |   |
|                          |
| <----------------------- |
|   | 1 | 1 | payload |    |
|                          |
| -----------------------> |
|   | 2 | 1 | payload |    |
|                          |
| <----------------------- |
|        | 2 | 2 |         |


Group stream structure
######################
######################

For group streams the server hosting the group chat maintains a list of
all active streams in the group and all active users.

Any change in the list is sent to all clients that participate in group
stream.

When the client connects to group stream, the server sends a list of
all existing streams to the client. Then the client may send requests to join
or leave each stream.
