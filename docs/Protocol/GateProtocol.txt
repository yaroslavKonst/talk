Overview
########
########

Gate protocol is used for communication between servers.

It is expected to run over TCP connection.

Handshake
#########
#########

Notes on cryptography
#####################

Key exchange and derivation scheme: keys are derived from the same shared
secret calculated via key exchange. The shared secret is then hashed with
the requesting server public key, the responding server public key and salt
(or a concatenation of salts if multiple must be used).

The hash size is twice as big as key. Then hash is split into two parts,
each part becomes a key for one direction in duplex channels.
This scheme is used for generation of all symmetric keys.

Nonce is a counter in big endian byte order. Sender must initialize the nonce.
Several first bytes are initialized as zeroes to provide a space for the
nonce value to grow. All subsequent bytes can be initialized as random values.
Receiver initializes its stored nonce value as zero.

Before encryption the sender increases nonce value by one.

The receiver checks whether the nonce in received message is greater than
stored from previous message. If it is not so, the message is discarded
and not decrypted, the session is closed. If the message was decrypted,
the receiver stores its nonce value for next message check.
In case of decryption failure the session is closed.

"message size": 32 bit unsigned integer;
"protocol version": 32 bit integer;
"encryption scheme": 32 bit integer;
all server names are strings with length prefix (see TypeFormats);
"session public key": byte array with public key of the selected
                      encryption scheme;
salts are 32 byte arrays.

Signatures sign the whole message if present.

Session public keys are public parts of one-time key pairs that are used only
in this session.

Session keys are derived from key pairs by key exchange and use salt 1 and
salt 2 concatenation during hashing.

Error codes are 32 bit integers.
Error code list:
REQUEST_RATE_LIMIT_REACHED
UNSUPPORTED_PROTOCOL_VERSION
UNSUPPORTED_ENCRYPTION_SCHEME
VERIFICATION_FAILURE

Status code is 32 bit integer and can be
SUCCESS
VERIFICATION_FAILURE

Verification
############

In case of verification failure the server may immediately close the connection
or respond with error code.

Verification of IP host names
-----------------------------

If the host name is an IP address then verification has the following
steps:
* verify that the connection is established with host with the same
  IP address as in the host name.

In this case the signature can't be checked. So, the server can apply
restrictions to the received data. For example, decline spam reports.

Verification of DNS host names
-----------------------------

If the host name is a DNS name then verification has the following
steps:
1. the name is resolved;
2. resolved IP address is compared with the IP address of the connected host;
3. IP address and host name are checked via rDNS request;
4. The server queries the TXT field on the same domain as the host,
   it must include a string "talkdkey=SIGNATURE_PUBLIC_KEY_HEX". All other text
   is ignored;
5. received data signature is checked using public key from DNS.

If DNS does not have key record step 5 can be omitted. But if DNS has key
record unsigned handshakes must lead to verification failure.

Note
----

Unsigned handshake provides protection only against eavesdropping, not
against MITM.

DoS protection
##############

The server may measure the rate of incoming requests. If the request rate
for some IP address exceeds maximum allowed rate, then the server may
send the "REQUEST_RATE_LIMIT_REACHED" command instead of Ack and close
the connection.

Session
#######
#######

Low level protocol
##################

Low level protocol runs on top of underlying TCP connection.

It sends data as a chunk sequence with the following chunk format:
| chunk size (32 bit unsigned integer) | MAC | nonce | payload |

Chunk size field value can not be zero or exceed 4 KB.
It covers size of MAC, nonce and payload.

All chunks are encrypted with session keys corresponding to chunk transmission
direction. MAC and encryption cover payload.

Session protocol
################

The session protocol runs on top of low level protocol and
is based on commands with the following structure:
| command size | command id | payload |

Response structure:
| response size | payload |

Command size field covers command identifier and payload, response size
field covers payload.

All size fields introduced in this subsection are 64 bit unsigned integers,
command identifier is a 32 bit integer.

After the session start the server which initiated the session becomes the
session leader.

The session leader can initiate actions during the session, the other
server must not initiate any actions. When the session leader has finished
all planned actions it must close connection.

Both the connection initiator and responding server may maintain connection
timeouts. Timeout occurs if connection is not used for data transmission
for a period of time. If timeout is reached the server can close connection.

Maximum message size request
############################

Servers may define maximum command sizes. These limits apply to everything:
command sizes, maximum message header and body sizes.

If the message size field has too big value the message receiver may
immediately close session.

It may be useful to check maximum allowed command size beforehand.

sender                                   receiver
| --------------------------------------------> |
|           | GET_MAX_COMMAND_SIZE |            |
|                                               |
| <-------------------------------------------- |
|   | maximum size (64 bit unsigned integer) |  |

User public key request
#######################

sender                                   receiver
| --------------------------------------------> |
|         | GET_USER_KEY | user name |          |
|                                               |
| <-------------------------------------------- |
|       | status | user key (optional) |        |

Status codes:
SUCCESS
FAILURE

The key in the response is present only if the status is SUCCESS.
Failure status means that the requested user does not exist or the server
does not want to disclose user key for some reason.

Message delivery
################

Message delivery has the following scheme.

sender                                                      receiver
| ---------------------------------------------------------------> |
|                  | MESSAGE | message header |                    |
|                                                                  |
|                                                   +--------------|
|                                                   | verification |
|                                                   +--------------|
|                                                                  |
|                   optional, only reject case                     |
| <--------------------------------------------------------------- |
|  | TEXT | rejection reason description in human readable form |  |
|                                                                  |
| <--------------------------------------------------------------- |
|                     | verification status |                      |
|                                                                  |
|----------------------------------+                               |
| End of message transmission with |                               |
| failure if status is not ACCEPT. |                               |
|----------------------------------+                               |
|                                                                  |
| ---------------------------------------------------------------> |
|                        | message body |                          |
|                                                                  |
|                                                   +--------------|
|                                                   | verification |
|                                                   +--------------|
|                                                                  |
| <--------------------------------------------------------------- |
|                    | verification status |                       |

Message header verification may involve the following checks:
* destination fields must contain existing user and valid key;
* source field must contain correct source server name (relaying messages from
  other servers is not allowed);
* message body size limit;
* spam filter;
* user defined restrictions (blocked users list etc.);
* whether this message is a duplicate of the existing one.

If any verification step is failed, then message delivery is interrupted,
sender may be informed about rejection reason via verification status.
Message receiver can provide more detailed error description via text message.

Header verification status list:
ACCEPT -- header is OK, proceed.
REJECT -- header is rejected, no details are given.
REJECT_INVALID_DESTINATION_USER -- destination user does not exist or invalid
                                   destination host name.
REJECT_INVALID_DESTINATION_KEY -- destination key is not valid.
REJECT_INVALID_HEADER -- header is ill formed and caused parsing failure.
REJECT_MESSAGE_TOO_BIG -- reported message body is too big to be processed.
REJECT_SENDER_BANNED -- sender was banned by the user.
REJECT_SENDER_KEY_BANNED -- sender key was banned by the user.
REJECT_SPAM -- spam filter did not allow the message to pass.
REJECT_EXISTS -- message with the same header already was delivered.

Message body verification status list:
ACCEPT -- message body is OK, message is accepted for delivery.
REJECT -- message body was rejected, no details.
REJECT_INVALID_SIZE -- message body size differs from the data in message
                       header.

######

sender                                   receiver
| --------------------------------------------> |

|                                               |
|                                 +-------------|
|                                 | user answer |
|                                 +-------------|
|                                               |
| <-------------------------------------------- |
|              | peer response |                |
|                                               |
|      +---------------------------------+      |

|      |   with failure if response is   |      |
|      |           not ACCEPT.           |      |

|                                               |
| <-------------------------------------------> |
|              | FRAME | payload |              |

|                                               |
| <-------------------------------------------> |
|                | STREAM_END |                 |

Request and peer response structure are described in client protocol.

Verification includes checks for user existence, user defined rules,
block lists, spam filters etc.

Stream control logic is described in the client protocol specification.

Since it may take a significant amount of time to answer or the channel may
be unused for some time during active stream connection it is allowed to
send keep alive commands during stream sessions to prevent session timeout.

Keep alive messages are allowed only after STREAM_REQUEST response if
response is WAITING_FOR_ANSWER and until STREAM_END command or DECLINE peer
response.

sender                                   receiver
| <-------------------------------------------> |
|                | KEEP_ALIVE |                 |

Sender is responsible for timeout tracking. If session is near timeout time
sender must send KEEP_ALIVE command. Receiver must respond with the same
command.

User presence
#############

Detailed description of presence status sharing is available in Client protocol
specification.

All data that is marked as encrypted, MAC and nonce fields are processed by
client software that has access to user private keys. It allows to ensure
authenticity and consistency of presence data.

Subscription:
sender                                                               receiver
| ------------------------------------------------------------------------> |
| | PRESENCE_SUBSCRIBE | name | key | timestamp | MAC | nonce |...          |
|                                                                           |
|                                                ...| encrypted user name | |
|                                                                           |
|                                                            +--------------|
|                                                            | verification |
|                                                            +--------------|
|                                                                           |
| <------------------------------------------------------------------------ |
|                           | response status |                             |

Response status list:
SUBSCRIBED -- status updates will be sent, subscription is active.
DECLINE -- server refuses to disclose status data.

Unsubscribe message can be sent by any side to notify that subscription
is expired or is not longer needed.
sender                                                               receiver
| ------------------------------------------------------------------------> |
| | PRESENCE_UNSUBSCRIBE | subscribed user name | status sender user name | |

Presence status update:
sender                                                               receiver
| ------------------------------------------------------------------------> |
| | PRESENCE_STATUS | presence status | name | key | MAC | nonce |...       |
|                                     \---------------------------...       |
|                                                    optional               |
|                                                                           |

|                                              ...---------------------/    |

Presence status list:
OFFLINE -- all clients are offline or don't want to respond.
ONLINE -- client is online and responded. Further data is in encrypted part.

Spam protection
###############

The server may maintain a list of IP addresses that are suspicious due to
sending spam.

Spam rating is based on spam points. Each point means one server that
marked this address as spam sender. Each server may set its own threshold
for IP addresses. Overcoming the threshold leads to rejection of the
messages from the spam sending server.

Each record in the spam database contains an IP address and a list of
servers who received a message from the address and considered it to be
spam. The size of the list is the spam score of the address.
Each entry in the list must be signed by the server's key in order to prevent
spam reporting from nonexistent servers.

The servers may exchange their spam databases during connections.
During data acquisition the receiving server must verify each line.

The lifetime of one spam entry is one year. After this period it must be
deleted from the spam database.

The administrator of the server may ask the server to exchange spam data
with any other server.

Users can ban sources of unwanted messages, so this subsystem is targeted
on the large scale spam senders. Small scale spam can be eliminated using
manual bans by users.
