Overview
########
########

The client protocol is used for connection between server and client.
It performs authentication and establishes encrypted connection.
All data is bitwise xor-ed with a stream of pseudo-random numbers (scrambled)
in order to make it harder for an eavesdropper to identify the protocol
and parse the data.

The client and the server are assumed to know each other's public keys.
It is achieved by key exchange during user registration on the server.

The client protocol is expected to run over TCP connection.

Some types used in this document are described in TypeFormats.txt.

Handshake
#########
#########

Handshake is the initial part of the client protocol.
It is used for authentication via challenge-response
scheme and establishing an encrypted channel.

It consists of three steps.

client                                                         server
| ----------------------------------------------------------------> |
| | scrambler init | syn size |...                                  |
|                  \-----------...                                  |
|                                                                   |
|     ...| protocol version | encryption scheme |...                |
|     ...----------------------------------------...                |
|                   authenticated                                   |
|                                                                   |
|       ...| random salt 1 | one time salt | one time key |...      |
|       ...-----------------------------------------------/         |
|                                                                   |
|                                      ...| MAC | nonce | name |    |
|                                                       \------/    |
|                                                       encrypted   |
|                                                                   |
| <---------------------------------------------------------------- |
| | scrambler init | SynAck size | MAC | nonce |...                 |
|                  \-------------/                                  |
|                   authenticated                                   |
|                                                                   |
|            ...| protocol version | encryption scheme |...         |
|               \---------------------------------------...         |
|                                                                   |
|      ...| challenge | server session public key | random salt 2 | |
|      ...--------------------------------------------------------/ |
|                    encrypted                                      |
|                               OR                                  |
|  | scrambler init | SynAck size | UNSUPPORTED_ENCRYPTION_SCHEME | |
|                               OR                                  |
|  | scrambler init | SynAck size | UNSUPPORTED_PROTOCOL_VERSION |  |
|                                                                   |
| ----------------------------------------------------------------> |
| | MAC | nonce | challenge response | client session public key |  |
|               \------------------------------------------------/  |
|                                  encrypted                        |
|                                                                   |
|------------------------+                 +------------------------|
| Session key generation |                 | Session key generation |
|------------------------+                 +------------------------|

Notes on cryptography
#####################

Key exchange and derivation scheme: keys are derived from the same shared
secret calculated via key exchange. The shared secret is then hashed with
the server public key, the client public key and salt (or a concatenation
of salts if multiple must be used).

The hash size is twice as big as key. Then hash is split into two parts,
each part becomes a key for one direction in duplex channels.
This scheme is used for generation of all symmetric keys.
For encryption in channels with only one direction only the first resulting
key is used.

Nonce is a counter in big endian byte order. Sender must initialize the nonce.
Several first bytes are initialized as zeroes to provide a space for the
nonce value to grow. All subsequent bytes can be initialized as random values.
Receiver initializes its stored nonce value as zero.

Before encryption the sender increases nonce value by one.

The receiver checks whether the nonce in received message is greater than
stored from previous message. If it is not so, the message is discarded
and not decrypted. If the message was decrypted, the receiver stores its
nonce value for next message check.

Step 1: Syn
###########

client                                                         server
| ----------------------------------------------------------------> |
| | scrambler init | syn size |...                                  |
|                  \-----------...                                  |
|                                                                   |
|     ...| protocol version | encryption scheme |...                |
|     ...----------------------------------------...                |
|                   authenticated                                   |
|                                                                   |
|       ...| random salt 1 | one time salt | one time key |...      |
|       ...-----------------------------------------------/         |
|                                                                   |
|                                      ...| MAC | nonce | name |    |
|                                                       \------/    |
|                                                       encrypted   |

"scrambler init": byte;
"syn size": 32 bit unsigned integer, length of all fields except
            scrambler init;
"protocol version": 32 bit integer;
"encryption scheme": 32 bit integer;
"random salt 1": 32 random bytes;
"one time salt": 32 random bytes;
"one time key": public key of selected encryption scheme;
"name": name string without prefix with string size.

The client generates random salt 1 and generates handshake keys using its
private key, stored server public key and salt 1.
A pair of handshake keys is used only during handshake for authentication.
Each key is used for one direction: key 1 is used from server to client,
key 2 is used from client to server.

The client generates one time salt and generates one time key pair
to encrypt the user name and sign the whole Syn message.

Then the client generates a symmetric key for name encryption by exchanging
between one time private key and stored server public key.

Then the client sends its encrypted user name, one time key and salts to
the server.
One time keys for user name are wiped.

All encrypted and authenticated fields are protected by one MAC.
User name is encrypted, other authenticated data is processed as associated
data in single AEAD call.

The server checks protocol version and encryption scheme.

Then the server uses the one time salt and key to generate a symmetric key.
This key allows to decrypt the user name and proceed to its verification.

Then the server uses the salt 1 and generates two handshake session keys by
key exchange between server private key and stored client public key.

If the syn size field is too big to have a valid user name the server can
state that handshake is failed and close the connection.

Step 2: SynAck
##############

client                                                         server
| <---------------------------------------------------------------- |
| | scrambler init | SynAck size | MAC | nonce |...                 |
|                  \-------------/                                  |
|                   authenticated                                   |
|                                                                   |
|            ...| protocol version | encryption scheme |...         |
|               \---------------------------------------...         |
|                                                                   |
|      ...| challenge | server session public key | random salt 2 | |
|      ...--------------------------------------------------------/ |
|                    encrypted                                      |
|                               OR                                  |
|  | scrambler init | SynAck size | UNSUPPORTED_ENCRYPTION_SCHEME | |
|                               OR                                  |
|  | scrambler init | SynAck size | UNSUPPORTED_PROTOCOL_VERSION |  |

"scrambler init": byte;
"SynAck size": 32 bit unsigned integer, message size without scrambler init;
"protocol version": 32 bit integer;
"encryption scheme": 32 bit integer;
"challenge": 64 bytes;
"server session public key": key size for selected encryption scheme;
"random salt 2": 32 random bytes.

Notifications about unsupported protocol properties are 32 bit integers.

The server generates new key pair that will be used for session key
generation only for this session.

The server generates random 64 byte challenge and salt 2.

The protocol version and encryption scheme are added to the message
to allow client to check whether the server received the proper values of
these parameters.

Then the server encrypts all data with the handshake key 1 and
sends it to the client.

If the client asked for unsupported protocol the server must send notification
about it and close the connection.

Step 3: Ack
###########

client                                                         server
| ----------------------------------------------------------------> |
| | MAC | nonce | challenge response | client session public key |  |
|               \------------------------------------------------/  |
|                                  encrypted                        |

The client receives SynAck from the server and decrypts it.
The client must check the correctness of protocol version and encryption
scheme.

Then the client generates a new key pair for the new session.

Then the client sends challenge response and its session public key both
encrypted by handshake key 2 back to the server.
On this point the client considers that the handshake is finished successfully.

Since the messages on the client side are decrypted with handshake key 1 and
encrypted by another one the challenge will be received, decrypted and
encrypted with another key. It allows the server to verify whether the
client has the appropriate private key.

The server decrypts the challenge and verifies it. If it is correct then
the server considers that the handshake is finished successfully.

When handshake is considered successful, the client and the server generate
session keys by exchange between one time key pairs. The session keys are
additionally hashed with salt 1 and salt 2. Key 1 is used for server to client
direction, key 2 is used for the opposite direction.

After the session key generation one time key pairs are wiped.

In case of failure any side must interrupt the session by closing the TCP
connection. Timeout is also considered as a failure and can cause consequences
from protection system.

DDoS protection
###############

The server may maintain a list of bad IP addresses. If handshake requests
from some IP address fail with a high rate, the server may mark this address
as bad. Connections from bad IP addresses are closed immediately after accept
or after a time delay. No request processing on the server side is done at all.

Session
#######
#######

After the successful handshake the client and the server have encrypted
duplex channel for communication. Each direction has its own session key.

Low level protocol structure
############################

On low level the protocol maintains a set of channels.
Each channel has a static priority: channels with lower index have higher
priority.

When a message is sent, it is split into chunks at most 4 KB of size.
Chunk length can not be zero.

If multiple channels have enqueued chunks to be sent, a chunk from
a channel with higher priority is selected.

Each chunk is sent with a length prefix and channel ID:
| chunk size | MAC | nonce | channel ID | payload |
                           \----------------------/
                                   encrypted

Chunks are encrypted before being sent via the underlying TCP connection
after stream selection. Since nonces are assigned only at encryption time,
after stream selection, the nonce counter is maintained per direction at
the connection level, not per channel.

Chunk size (64 bit unsigned integer) covers MAC, nonce, channel ID and
payload size.

High level protocol structure
#############################

Data arrays are sent over the channel system in length prefixed manner:
| data length (64 bit unsigned integer) | payload |

When the data array is going to be sent, it is assigned to a channel number
that must be used during transmission.

Command structure
#################

Commands are sent as data arrays.
Larger commands (for example, message sending commands) must be sent via
channels with low priority since large commands may be transmitted for a
significant period of time so smaller commands must have an ability to
pass via channels with high priority during large command transmission.

Command structure:
| command id | optional payload |

Some commands may require answer from the other side. Responses have the same
structure:
| command id | optional payload |

"Command id": 32-bit unsigned integer.

If the same command may be sent both by server and client, this command
must not have answer since it will be impossible to distinguish answers
from original commands.

Command list
############

Keep alive
----------

| KEEP_ALIVE | timestamp |
"timestamp": a 64-bit signed integer.

This command is used when the session is idle in order to check the
connection and prevent timeout. It is initiated by the client. When
the server receives this command it must send the same command with
the same parameter as response.

Managing server host name
-------------------------

The client must embed server host name into the message header before header
signing. So, the client must get actual host name from the server.
Since the server may be configured to accept client and peer connections on
different network interfaces it may be impossible to get appropriate host
name from the client configuration.

| GET_HOST_NAME |

This command is sent by the client to get actual server host name.

Response:
| GET_HOST_NAME | name |
"name": string.

The server must send this command as a response to the client's request.
The server must send it on its own without a request in case of configuration
update.

Maximum message size query
--------------------------

| GET_MAX_MESSAGE_SIZE |

This command is sent by the client to query message size limit. Size limit
is applied to all commands sent to the server from the client. If the client
makes an attempt to send a command that exceeds limit the server may
close the session immediately.

Response sent by the server:
| GET_MAX_MESSAGE_SIZE | maximum size |
"maximum size": 64 bit unsigned integer.

Managing database ID
--------------------

The server stores data as a sequence of modifications and tells the client
the ID of the latest item, sent to the client. It allows to synchronize
data between the server and the client.

Example:
[sent message1] -> [message1 is marked as delivered] -> [received message2] ->
-> [message2 is marked as read] -> [contact A is added to the contact list]

Each item in the sequence has its unique 32 byte identifier.

When it is needed to synchronize local client's database with the server's
database the server needs to know the ID recorded by the client. This ID
points to the latest item in the event sequence that was sent to the client.

| REQUEST_ID |

Sent by the server to get database ID, recorded by the client.

If the client does not want to update local database it can ignore this command.
In this case the server will not send any updates.

Response, sent by the client:
| REQUEST_ID | id |
"id" : 32 byte array with the ID.

The client can't initiate database update on its own. It is always started
by the server in two cases: in the beginning of a new session and in
case of new data being added to the database.

If the client sends ID that does not exist in the server database, the server
must assume that the client does not have any existing updates. So, the
server must send the full database to the client.

| UPDATE_ID | id |

This command is sent by the server to make the client to record a new
ID. It does not need a response.

It must be sent after database item transmission to ensure consistency.

The server may send the same item several times if the client's
database has lost consistency and the client requested the wrong item.
The client must be ready for such situation and silently ignore received
items that are already in the client's local database.

Account settings
----------------

User can set global account settings. These settings are applied to
all inbound messages and calls.

| GET_ACCOUNT_SETTINGS |
Sent by the client to request account settings.

Response:
| GET_ACCOUNT_SETTINGS | allow messages only from contact list |...
...| allow calls only from contact list | show in contact list |

All response parameters are bytes interpreted as boolean values.

| SET_ACCOUNT_SETTINGS | allow messages only from contact list |...
...| allow calls only from contact list | show in contact list |
Sent by the client to set new settings. Has the same arguments as
GET_ACCOUNT_SETTINGS response. This command does not have response.

Managing contacts and their keys
--------------------------------

| ADD_CONTACT | name |
"name": string.

This command is sent by the server or the client to add a new contact to the
contact list.

| UPDATE_CONTACT_KEY | name | key | validated | blocked | default |
"name": user name, string.
"key": user key, 32 byte array.
"validated": byte, considered as logical value. Whether to consider this key
             as checked for authenticity.
"blocked": byte, considered as logical value. Whether to accept messages
           containing this key.
"default": byte, considered as logical value. Whether to use the key for
           new messages.

This command is used for contact key management.

| BLOCK_CONTACT | name | value |
"name": string.
"value": 8 bit unsigned int.

This command sets whether contact is blocked.

| REMOVE_CONTACT | name |
"name": string.

This command permanently removes a contact. No data is saved.

Contact book request
--------------------

| LIST_CONTACTS |

This command allows to request server contact list. It includes all users
registered on the server that allowed broadcasting of their contact data.

Response:
| LIST_CONTACTS | contact number | { | name | public key | }
"contact number": 32 bit unsigned integer.
"name": string.
"public key": 32 byte key.

Managing messages
-----------------

| OFFER_MESSAGE | peer name | header hash |
"peer name": string;
"header hash": 32 byte array.

This command is sent by the server to offer a new message to the client and
prevent message transmission if the client already has a message with
the same header hash.

Client response:
| OFFER_MESSAGE | answer |
"answer": byte, whether to send message to the client.

| SEND_MESSAGE | message attributes | message data |
"message attributes": current mask of message attributes, 32 bit integer;
"message data": array with concatenated message header and message body.

This command is sent by the client or the server to send a new message.

| UPDATE_MESSAGE | peer name | message header hash |...
...| attribute ID | attribute value |
"peer name": string;
"message header hash": 32 byte array;
"attribute id": 32 bit insigned integer;
"attribute value": byte.

This message is sent by the client or the server to update message attribute.

| DELETE_MESSAGE | peer name | message header hash |
"peer name": string;
"message header hash": 32 byte array.

This message is sent by the client or the server to delete message.

| REMOTE_MESSAGE_UPDATE | message header |...
...| MAC | nonce | attribute ID | attribute value |
                 \--------------------------------/
                             encrypted

This message is sent by the client to send message update to remote server.
For example, it allows to notify the other user that the message was read.
It has the same structure as original message but instead of message
body it has encrypted attribute properties that must be sent. Header is a
full copy of original message header, so encryption header (MAC, nonce)
for this message is new and located outside of message header. In-header
nonce is not used for encryption purpose.

Managing groups
---------------

Group managing commands can be sent not only to the user's server,
but on remote servers too (via the user's server). So, these commands use
special headers for encryption and authentication:
| group host | group host key | user name | user key | timestamp | MAC | nonce |

The encrypted payload goes after the header.

Response header has the same structure.

Command list:

* | CREATE_GROUP | group name |
  This command can be sent only to the server where the user is registered.
  So, it does not have encryption. The user which requested group creation
  is automatically added to it and gets a full set of capabilities.

  Response list:
  SUCCESS
  GROUP_EXISTS
  FORBIDDEN

* | DELETE_GROUP | header | group name |
  Delete existing group. Capability: REMOVE_USERS.

  Response list:
  SUCCESS
  NO_CAPABILITY
  SERVER_UNREACHABLE
  NONEXISTENT_GROUP

* | ADD_USER | header | group name | user name | user public key |
  Add new user to the group. Capability: ADD_USERS.

  Response list:
  SUCCESS
  NO_CAPABILITY
  SERVER_UNREACHABLE
  USER_EXISTS

* | REMOVE_USER | header | group name | user name |
  Remove user from the group. Capability: REMOVE_USERS. Exception: any user
  always can remove themselves. And any user can ban the group to avoid getting
  any messages from it.

  If the group becomes empty as a result of user removal, it is deleted.

  Response list:
  SUCCESS
  NO_CAPABILITY
  SERVER_UNREACHABLE
  USER_NONEXISTENT

* | UPDATE_USER | header | group name | user name | user public key |
  Update existing user's key. Capability: UPDATE_USERS.

  Response list:
  SUCCESS
  NO_CAPABILITY
  SERVER_UNREACHABLE
  USER_NONEXISTENT

* | SET_USER_CAPABILITIES | header | group name | user name | capabilities |
  Set capabilities for an existing user. Capability: SET_CAPABILITIES.

  Response list:
  SUCCESS
  NO_CAPABILITY
  SERVER_UNREACHABLE
  USER_NONEXISTENT

* | GET_CAPABILITIES | header | group name | user name |
  Get requesting user's capabilities. Capability is not required, any user
  can request own capabilities.

  Response structure:
  | status | capabilities (optional) |

  Response status list:
  SUCCESS
  SERVER_UNREACHABLE

Managing streams
----------------

Requesting new connection by client:
client                                     server
| --------------------------------------------> |
|            | STREAM_INIT | request |          |
|                                               |
| <-------------------------------------------- |
|            | STREAM_INIT | status |           |
|                                               |
|  +-----------------------------------------+  |
|  | If the status is not WAITING_FOR_ANSWER |  |
|  |  stream initialization ends here with   |  |
|  |    failure. Stream is not started.      |  |
|  +-----------------------------------------+  |
|                                               |
| <-------------------------------------------- |
|      | STREAM_RESPONSE | peer response |      |

Request structure:
| source name | source key | destination name | destination key |...
...| salt 1 | MAC | nonce | session public key | challenge |
                          \--------------------------------/
                                      encrypted

"status" is a 32 bit unsigned integer.

Status types:
WAITING_FOR_ANSWER
ERROR
YOU_ARE_IN_CALL
SERVER_OFFLINE
USER_OFFLINE
USER_BUSY
USER_NONEXISTENT
INVALID_DESTINATION_KEY
CALL_PROHIBITED
YOU_ARE_BANNED
YOUR_KEY_IS_BANNED
PARSING_FAILURE

If the status is not WAITING_FOR_ANSWER then stream is not started.

Peer response structure:
| MAC | nonce | response | salt 2 | session public key | challenge response |
              \-------------------------------------------------------------/
                                        encrypted

"response": 32 bit unsigned integer.

Peer response types:
ACCEPT
DECLINE

If the peer response is ACCEPT then the stream is started.
Response is encrypted to ensure answer authentication.

Responding on connection request:
client                                     server
| <-------------------------------------------- |
|          | STREAM_REQUEST | request |         |
|                                               |
| --------------------------------------------> |
|          | STREAM_REQUEST | response |        |

Response types:
ACCEPT
DECLINE

Active stream session:
client                                     server
| <-------------------------------------------> |
|           | STREAM_DATA | payload |           |
|                                               |
|                - - - - - - -                  |
|                                               |
| <-------------------------------------------> |
|           | STREAM_DATA | payload |           |
|                                               |
| <-------------------------------------------> |
|                 | STREAM_END |                |

Bidirectional arrows mean that commands with stream payload may be sent by
any side at any time.

Stream end command may be sent by any side. When any side receives or sends
this command, the stream session is considered to be closed. This command
does not require an answer.

STREAM_END command may be sent not only during the active session, but
during stream initialization. In this case initialization must be interrupted
and considered unsuccessful.

One user may have only one active stream session at a time.

Requesting presence and responding presence requests
----------------------------------------------------

To prevent active polling, presence data exchange is implemented via
subscriptions.

When a user logs in and opens a chat, the client sends a presence subscription
request to the peer. If presence data sharing is allowed, the server sends
user status and adds a subscription, so it will automatically send status
updates when necessary without requests. A subscription has a limited
duration to prevent its infinite lifetime. In the end of subscription
the server notifies the requesting server about it. The requesting server can
stop the subscription at any time if it is not needed. For example, if the
user logged out.

Requesting presence:
client                                                                 server
| ------------------------------------------------------------------------> |
| | PRESENCE | name | key | timestamp | MAC | nonce | encrypted user name | |
|                                                                           |
| <------------------------------------------------------------------------ |
|    | PRESENCE | status | name | key | MAC | nonce | encrypted status |    |
|                        \---------------------------------------------/    |
|                                           optional                        |

Responding presence:
client                                                                    server
| <--------------------------------------------------------------------------- |
| | PRESENCE_REQUEST | name | key | timestamp |...                             |
|                                        | MAC | nonce | encrypted user name | |
|                                                                              |
| ---------------------------------------------------------------------------> |
| | PRESENCE_REQUEST | status | name | key | MAC | nonce | encrypted status |  |
|                             \---------------------------------------------/  |
|                                                optional                      |

Status list:
OFFLINE
RESPONDED

Encrypted status:
| status ID | status text |

Status ID list:
ONLINE
BUSY
AWAY

Status text is a string.
